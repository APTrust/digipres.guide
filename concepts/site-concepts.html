Three ways to put the toolkit on the web

Each concept below takes the same manuscript, Digital Preservation Appraisal & Selection: Toolkit for Organizations with Limited Resources, and gives readers a different way in. The mockups use real text from the November 10 draft and you can click around in them.

What we need from the team: pick the front door. The book's chapters, interactive checklists, glossary, and tool lists show up in all three. The concepts differ in what a first-time visitor sees and does first.

Same in every concept

  • Authors edit Markdown files in a GitHub repo and propose changes through pull requests.
  • GitHub Actions builds the static site and publishes it to GitHub Pages.
  • CLIR produces the official PDF. The site links to it and doesn't build its own.
  • Glossary terms, tools, and further reading live in data files (glossary.yml, tools.yml) and are written once, then reused across the site.
  • Static full-text search, no server needed.
  • Checklists save progress in the reader's own browser. We store no accounts or personal data.
  • Built and tested to WCAG 2.2 AA.

Concept A · book first

The Field Guide

The online edition of the book. Readers move through chapters in order, with glossary definitions on hover, notes in the margin, checklists they can tick off as they read, and a clear "cite this" and PDF download. It reads as a CLIR publication.

Best for

  • Readers who come from CLIR, a syllabus, or a citation and want the whole argument.
  • Instructors assigning a chapter by URL.
  • Staying closest to the version of record.

Tradeoffs

  • Newcomers in a hurry still have to find their own place in a long read.
  • Checklists sit inside chapters, so they are harder to use as a standalone worksheet.
  • Looks the most like other online books.

Build

A Quarto book project. Quarto is one installed tool with no npm. It gives the book layout, footnotes, citations from Zotero, and cross-references out of the box. Without a PDF to make, Hugo could also build this concept, with a little more template work for margin notes.

Concept B · the model is the map

The Cycle

The home page is the toolkit's own five-stage cycle: Prepare, Curate, Check, Transfer, Save & Maintain. Each stage opens a working page with its checklist, the tools for that step, and a link into the full chapter. The site's navigation follows the book's four phases (Learn, Get Ready, Start Doing, Keep Doing).

Try it: click a stage on the cycle and tick a few items. Progress is kept per stage.

Best for

  • Practitioners who already decided to start and want to know what to do this week.
  • Workshops and trainings where the cycle diagram is the teaching tool.
  • Return visits: "where was I in the cycle?"

Tradeoffs

  • The Learn and Get Ready chapters don't map to the five stages, so they need their own pages outside the cycle.
  • The cycle as drawn has five stages, while the "Start Doing" text describes four headings. The manuscript should settle on one.
  • The custom home page and stage templates take more design work.

Build

Hugo, a single pinned binary with no package manager. Chapters are Markdown in content/. Each stage's checklist and tools live in data/stages.yaml, and a Hugo template draws the SVG cycle from it, so changing a stage updates the diagram, the stage page, and the printable worksheet. The checklists use about 100 lines of plain JavaScript and no libraries. Pagefind, also a standalone binary, indexes the built site for search.

Concept C · meet them where they are

Start Where You Are

Answer two questions first: what are you working with, and what can you put toward it? The site then shows a short, ordered path through the toolkit with the tools and storage that fit. It acts on the book's promise to "meet practitioners where they are." The three starting situations come from the manuscript's own example workflows.

Try it: pick a situation and a resource level, and watch the path and storage advice change. Search the glossary on the right.

    Best for

    • The book's core audience: small, less-resourced organizations unsure where to begin.
    • Sharing a link that already fits someone's situation, like "here's your path."
    • Showing that you can start with no budget at all.

    Tradeoffs

    • Someone has to write and maintain the path logic. It is new editorial content that isn't in the manuscript yet.
    • A path can feel like an answer key, so it needs clear "this is one route" framing.
    • The most custom build, and the most to test for accessibility.

    Build

    Hugo, pinned, with Markdown chapters. data/paths.yaml maps each situation and resource level to an ordered list of chapter sections, tools, and storage options. Hugo writes every combination out as its own static page, such as /start/legacy-media/no-budget/, so paths work and can be shared without JavaScript. A little plain script only swaps between them in place. The glossary panel reads data/glossary.yaml.

    A possible path

    If the team picks A alone, Quarto is the quickest route. If B or C is where we want to end up, start in Hugo from day one: launch the chapters with a book-style layout first, then add the cycle or pathfinder home page as a second release on the same content. That avoids moving off Quarto-specific Markdown later.

    Branding

    Does CLIR require Pocket Burgundy branding on a companion site, or can it carry its own identity with a CLIR credit? Ask CLIR before visual design starts.

    Where it lives

    Which GitHub organization owns the repo, and do we want a custom domain instead of the github.io address?

    Version of record

    Is the CLIR PDF canonical, with the site as a living edition? If the site changes after publication, how do we label versions and cite them?

    Upkeep

    Who reviews pull requests after launch, and how often do we check links and tool listings? Tools "come and go," as the draft says.
